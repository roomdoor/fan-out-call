# 측정 스크립트 설계 기록

왜 이렇게 됐는지만 적는다. 쓰는 법은 [`README.md`](README.md).

## 숫자를 로그가 아니라 DB에서 센다

처음에는 게이트웨이 로그를 `grep -c` 로 셌다. 두 가지가 걸렸다.

- 완료 여부를 "로그 개수가 15초 동안 안 변한다"로 추측해야 했고, SSM이
  한 번 삐끗해 못 읽으면 안 끝난 것으로 보였다. 그게 진짜 포화와 구분되지
  않았다.
- 카운터를 종류별로 두다 보니 어느 카운터에도 안 잡히는 상태가 생겼고,
  그 run 이 집계에서 통째로 빠졌다.

DB에는 같은 정보가 정확히 들어 있다. `status='IN_PROGRESS'` 가 0이면 끝이다.

## 조기 종료를 넣었다가 뺐다

"천장을 만나면 남은 RPM 회차를 건너뛴다"를 구현했다가 걷어냈다. 리뷰 다섯
번 동안 그 판정 로직과 그걸 지키려고 넣은 가드에서만 결함이 13건 나왔다.
대부분이 **멀쩡한 회차를 천장으로 오독해 남은 회차를 조용히 버리는** 종류라,
아끼는 시간(약 2시간)보다 위험이 컸다.

지금은 사람이 표를 보고 다음 판의 RPM 범위를 정한다.

## pool 4종을 한 번에 돌리지 않는다

`RPM ≈ pool / 9` 는 계산값이지 잰 값이 아니다. 4종을 한꺼번에 던졌다가
공식이 틀린 것으로 드러나면 60회차를 통째로 버린다. 첫 판(pool 512)이 눈금을
맞추고, 그 결과로 다음 pool 의 RPM 범위를 정한다.

## `fail_reason` 을 넣은 이유

`status='FAILED'` 하나에 세 가지가 섞여 있었다 — 은행을 다 호출했는데 성공이
0인 경우(부하 신호), 집계 단계에서 터진 경우(DB 부하), fan-out 자체가 예외로
끊긴 경우(코드 문제). DB만 보고 표를 만들면 뒤의 둘이 천장처럼 보인다.

`markRunFailed` 가 이미 `reason` 을 받아놓고 로그로만 흘리고 있었다.

## 합 검사는 run 상태 쪽에만 건다

은행 호출 버킷의 마지막 칸이 "위 셋이 아닌 실패" 라 분류가 빠짐없이 덮인다.
그래서 합이 항상 전체와 같고 아무것도 못 잡는다. 실제로 깨질 수 있는 건
run 상태 쪽이다 — `RunStatus` 에 값이 하나 늘면 그 run 들이 어느 칸에도 안
잡힌다.

## `DURATION` 을 4분 밑으로 안 내린다

천장 근처에서는 큐가 초과분을 먼저 먹기 때문에 포화가 늦게 나타난다.
pool 512 / 큐 200 / 60 RPM 이면 초당 2.6콜이 밀려 큐가 차는 데 약 77초다.
2분으로 줄이면 거부 구간이 43초뿐이라 천장을 실제보다 높게 잡는다.

## 회차 실패가 다른 회차로 번지지 않게 한다

기동 실패, k6 비정상 종료, DB 실패, 드레인 상한, 집계 불일치가 전부 같은
결과다 — 그 회차만 `valid=false` 로 두고 다음 회차는 그대로 진행한다.
실패 판단이 여러 곳에 흩어져 있으면 한 곳을 고쳐도 형제 경로가 남는다.
